# Architecture

Design specification is not restated here — `handoff-flutter/` is canonical for
anything visual or behavioural. This document covers how that specification is
built.

## Stack

| Layer | Choice |
|---|---|
| Client | Flutter 3.47 (Android · iOS · Web) |
| Language | Dart 3.13, on both sides |
| State | Riverpod |
| Routing | go_router |
| Server | Dart, on Shelf + shelf_router |
| Database | PostgreSQL 16 |

## Layout

```
apps/mobile/            the Flutter application
packages/
  ejadah_ui/            design tokens and the Ejadah component family
  ejadah_core/          failures, HTTP client, storage, analytics
  ejadah_models/        typed models shared by app and server
  ejadah_localization/  ARB generated from the canonical string tables
server/                 the Dart backend, and its SQL migrations
tool/                   importers, seeders, generators, dev.sh
handoff-flutter/        the canonical specification (never edited by code)
data/                   the canonical datasets
```

`ejadah_models` is shared by both sides, so a renamed field cannot silently
diverge between what the server sends and what the client expects.

## Why Shelf rather than Serverpod

The brief prefers Serverpod "unless repository analysis reveals a strong reason
another Dart-native server framework is substantially better". Three
project-specific reasons made Shelf the better fit:

1. **Unauthenticated routes are core product surface.** `/dr/{slug}`,
   `/verify/{code}` and guest roadmap generation are the growth and trust loops.
   Shelf makes authentication per-route middleware rather than an ambient
   session model, and a guest is a first-class caller throughout.
2. **The schema is dataset-shaped, not codegen-shaped.** 199 programme rows with
   40 source fields and 23 bilingual guides with nested children are imported
   from fixed files. Server-side filtering, pagination and the booking guarantee
   all want deliberate SQL, not generated CRUD.
3. **The booking guarantee needs explicit control.** An exclusion constraint,
   `SELECT … FOR UPDATE`, and in-place hold conversion are the mechanism; they
   are clearest with direct transaction control.

Shelf is Dart-native and is the foundation Dart Frog itself builds on, so the
whole product stays in one language as required.

## Server layers

```
Route handler  →  Application service  →  Domain  →  Repository  →  PostgreSQL
```

No SQL above a repository. No HTTP types below a handler. The roadmap engine is
a pure function with no I/O at all, which is what makes it testable for
reproducibility.

## Modules

A modular monolith: one process, one database, clear boundaries. No
microservices, no broker, no cache tier — nothing measured here justifies them.

`auth` · `career` · `roadmap` · `people` (marketplace and booking) ·
`profile` · platform services (notifications, analytics, storage, jobs).

## Decisions worth knowing

**The gate is enforced server-side.** A guest's roadmap is truncated to two
stages by the *server*. Blurring in the client would leave the full result one
inspector away, which is not a gate.

**The roadmap is deterministic and reads only Ejadah's rows.** No model call, no
inference, no external lookup. `RoadmapEngine` takes `today` as a parameter
rather than reading the clock, so its output is a pure function of its inputs.
The reference-data version is stored on every result so reproducibility can be
asserted against a known dataset.

**One reservation timeline.** Holds and confirmed sessions are rows in one
table, so a single exclusion constraint spans both. Two callers racing for a
slot cannot both commit — the database refuses the second, and the API turns
that into the approved conflict copy.

**Prices are computed server-side.** A price arriving from a client is never
trusted, and never even read.

**"Pending source" is a type, not a formatting choice.** `Sourced<T>` carries a
value with its provenance and cannot be rendered without going through the
pending check.

**The payment split is legal.** Courses are in-app purchase only; sessions and
the physical card are external checkout. These look inconsistent; they are law,
and must not be harmonised.

## Generated, and committed

`packages/ejadah_ui/lib/src/tokens/tokens.g.dart` from `DESIGN_TOKENS.json`, and
the ARB files from the string tables. Both are committed so a build never
depends on a generator having been run, and both are regenerated by `tool/`
scripts rather than edited.
