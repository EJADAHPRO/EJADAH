Epic 1: Identity, Registration, and Roles
This epic covers User Registration, Professional Profile, Multi-Role Architecture, Professional Verification Levels, and Social Login.
The objective is to establish the complete identity infrastructure — every user can register, verify, build their profile, hold multiple roles, and earn verification badges before any other platform feature is accessible.
US-1.1 — Email Registration
User Story As a dental professional, I need to register for an Ejadah account using my email address and password so that I can access platform features.
Acceptance Criteria
• Registration form must collect: email, password, name_arabic, name_english, specialty, user_type, country
• Password field must enforce: minimum 8 characters, one uppercase letter, one number, one special character — with inline validation before submission
• On successful submission, the system must create a user record with verification_status = unverified
• A 6-digit OTP verification email must be dispatched within 60 seconds
• User must be redirected to the email verification screen
• If email already exists, form must display: "An account with this email already exists. Did you mean to log in?"
• JWT access token and refresh token must be stored in HttpOnly cookies — never localStorage
Validate
• Submitting with a duplicate email must display the exact error message above — never a 500 error and never a generic message
• Submitting with a password shorter than 8 characters must be rejected inline before the form is submitted to the server
• Submitting with an Arabic name containing Latin characters must display: "Please enter your name in Arabic"
• Submitting with an English name containing Arabic characters must display: "Please enter your name in English"
• A network timeout during registration must display: "Something went wrong. Your information has not been saved. Please try again." — and must not create a partial user record
• A new user record must appear in the admin dashboard within 60 seconds of successful registration
US-1.2 — Email Verification via OTP
User Story As a newly registered user, I need to verify my email address by entering a one-time code so that my account is activated and I can access the platform.
Acceptance Criteria
• Verification screen must display a 6-digit OTP input field and a Resend code option
• OTP must be valid for 30 minutes from generation
• Maximum 5 failed attempts per OTP — after 5 failures the OTP is invalidated and the user must request a new one
• Maximum 3 OTP resend requests per hour — after 3, display: "Too many verification attempts. Please try again in 1 hour."
• On successful OTP entry: verification_status must be set to verified and user redirected to /onboarding/step-1
• Unverified accounts must be purged after 72 hours by a scheduled job
Validate
• Entering the correct OTP after it has expired must display: "This code has expired. We have sent you a new one." and automatically send a new OTP
• Entering an OTP from a previous resend (superseded OTP) must fail — only the most recently generated OTP is valid
• A 6th failed attempt must invalidate the current OTP and prompt the user to request a new one
• An unverified account attempting to access any feature beyond the verification screen must be redirected back to the verification screen
• The 72-hour purge job must be idempotent — running it twice must not cause errors or double-delete
US-1.3 — Professional Profile Completion
User Story As a verified user, I need to complete my professional profile with my credentials and background so that the platform can personalise my experience and my credentials are visible to others.
Acceptance Criteria
• Onboarding flow must prompt for: profile photo, specialty, user_type, university (required if student or graduate), graduation_year (required if graduate or practicing), bio_arabic, bio_english, linkedin_url, exam_target, exam_target_date
• Profile completion percentage must be calculated and displayed — updating in real time as fields are completed
• Profile photo must be under 5MB; accepted formats JPG, PNG, WEBP; system must resize to 400×400px on upload
• A profile below 70% completion must trigger a prompt on every login until completed
• name_arabic and name_english must be locked after the first certificate is issued — change attempts must display: "Your name is linked to issued certificates. Please contact support to update your name."
Validate
• Uploading a photo larger than 5MB must display: "Photo must be under 5MB. Please choose a smaller file."
• Uploading an unsupported file format must display: "Please upload a JPG, PNG, or WEBP image."
• Leaving university blank when user_type = student must display inline validation: "Please enter your university name."
• Setting an exam_target_date in the past must display: "Please select a future date for your exam target."
• A user with exam_target_date within 90 days must see a persistent dashboard banner: "Your [exam name] is in [X] days. View your preparation plan."
• Profile completion percentage must update without a full page reload
US-1.4 — Multi-Role Switching
User Story As a user with multiple roles, I need to switch between my roles from the navigation so that I can access the correct dashboard and features for each of my responsibilities.
Acceptance Criteria
• A role switcher must be visible in the navigation header for all users with more than one assigned role
• Switching roles must complete in under 1 second without a full page reload
• The dashboard, navigation items, and visible features must update to reflect the active role immediately after switching
• A user with only the student role must see zero tutor-facing, admin-facing, or content-creator-facing UI elements — these elements must not render at all
• platform_admin role must only be assignable by an existing platform_admin from the admin panel — never from the user-facing application
Validate
• An API call from a student attempting to access a tutor-only endpoint must return 403 with: "You do not have permission to perform this action."
• A user whose tutor role is suspended mid-session must have their next tutor-role API call return 403, and the frontend must redirect them to the student dashboard with: "Your tutor account is under review. You have been switched to your student account."
• A user attempting to self-assign platform_admin via API manipulation must receive a 403 response
• An institution_admin removed from their institution while logged in must be redirected to the student dashboard on their next page load
US-1.5 — Graduate Verification Badge Application
User Story As a dental graduate, I need to upload my degree certificate for verification so that I can display a verified graduate badge on my profile and become eligible to list as a tutor.
Acceptance Criteria
• Verification application form must collect: verification_type (graduate_verified), document upload (PDF/JPG/PNG, max 10MB), document_description
• On submission: a verification application record must be created with status = pending; a platform admin notification must be sent; user must receive: "Your verification application has been received. We will review it within 72 hours."
• Documents must be stored in AWS S3 private bucket — never publicly accessible; only platform_admin role can access them
• On approval: badge appears on user's profile within 5 minutes; user receives notification
• On rejection: admin must provide a rejection reason; user receives: "Your [verification type] application was not approved. Reason: [admin reason]. You can reapply with corrected documentation."
Validate
• Uploading a document in an unsupported format must display: "Please upload a PDF, JPG, or PNG file under 10MB."
• Attempting to access the S3 document URL directly without a signed URL must return 403
• A verification application where the 72-hour review window passes without admin action must trigger an automated reminder to platform_admin and display to the user: "Your application is still under review. We apologise for the delay."
• A user attempting to apply for exam_passed without first having graduate_verified must see: "Please complete graduate verification before applying for exam verification."
• An approved badge must appear on the user's public profile within 5 minutes of admin approval
US-1.6 — Exam Passed Verification Badge
User Story As a dentist who has passed a licensing exam, I need to upload my exam result certificate for verification so that my exam pass is displayed as a verified badge and increases my credibility as a tutor.
Acceptance Criteria
• Application form must collect: exam_type (EHC / DHA / HAAD / DOH / SCFHS / ORE), pass_certificate upload (max 10MB), pass_date
• User must already have graduate_verified status — the system must block this application if not
• On approval: badge displayed as "✓ [Exam Name] Passed" — not a generic badge
• Multiple exam passes (e.g. DHA and EHC) must each display as separate badges on the profile
• Same review SLA and rejection flow as US-1.5
Validate
• A user without graduate_verified attempting to apply must see the blocking message — the form must not submit
• An approved DHA badge must display exactly as "✓ DHA Passed" on the tutor listing and profile
• A user with both DHA and EHC passed must display both badges simultaneously on their profile
US-1.7 — Social Login (Google)
User Story As a prospective user, I need to register or log in using my Google account so that I can access Ejadah without creating a separate password.
Acceptance Criteria
• Google OAuth 2.0 flow must be supported on the registration and login screens
• On first Google login with a new email: new user record created; user routed to onboarding
• On Google login with an existing email/password account: display "An account with this email exists. Log in with your password to link your Google account." — do not auto-merge
• auth_provider field set to google on the user record
• JWT tokens returned in HttpOnly cookies on success
Validate
• If Google OAuth provider returns an error: display "We could not connect to Google. Please try again or register with email."
• Google login flow must complete in under 5 seconds on a standard mobile connection
• A new Google-authenticated user must reach the onboarding screen within 2 clicks of initiating social login
• A user who revokes Ejadah's Google permission must see: "Please log in with your email and password, or re-authorise Google access." on next login attempt
US-1.8 — Social Login (Apple)
User Story As a prospective user on an Apple device, I need to register or log in using my Apple ID so that I can access Ejadah quickly without a separate password.
Acceptance Criteria
• Sign in with Apple must be supported on the registration and login screens
• Apple private relay email (e.g. xyz@privaterelay.appleid.com) must be stored as the user's email — the user must be prompted to add a real email address in profile settings for certificate delivery
• All other behaviour mirrors US-1.7
Validate
• If Apple returns no email (user chose to hide): prompt the user to manually enter their email before completing registration
• A user who revokes Ejadah's Apple permission must see the appropriate re-authorisation message on next login
• Apple relay email must be stored correctly — not rejected as an invalid email format
Epic 2: Content Library and Editorial System
This epic covers the Study Library, Content Review Date System, Search and Filtering, Content CMS, and Revenue Share Tracking.
The objective is to make the complete content production and delivery infrastructure operational — content can be created, reviewed, published, discovered, read, and financially tracked from Day 1.
US-2.1 — Browse the Study Library
User Story As a subscribed dental professional, I need to browse the Arabic study library by subject so that I can find summaries relevant to my current area of study.
Acceptance Criteria
• Library home screen must display content organised by subject category with item counts per category
• Each item card must display: title_arabic, title_english, subject_tags, difficulty_level, estimated_read_time, last_reviewed_date, access status (locked or accessible)
• last_reviewed_date must be visible on every card — displayed as "Last reviewed: [Month Year]"
• Free tier users must see a preview of the first 20% of content for paywalled items, then a conversion prompt
• Items outside the user's tier must display a lock icon and upgrade CTA — never be hidden entirely
Validate
• A freemium user who has viewed 15 unique summaries in the current month must see a hard paywall on the 16th item regardless of whether it is a free-tier item
• An archived item must not appear in the library browse view under any circumstances
• A subscribed Professional Plus user must be able to open any published summary within 2 clicks from the library home screen
• The conversion prompt for a paywalled item must display the subscription price and a direct link to the subscription page — never more than one click to upgrade
US-2.2 — Read a Study Summary
User Story As a subscribed dental professional, I need to read a full Arabic study summary so that I can learn the material in my own language at my own pace.
Acceptance Criteria
• Full content must render with correct Arabic RTL layout — headings, bullet points, tables displayed correctly
• last_reviewed_date must be displayed below the title on the reading view
• System must record a content_view event with user_id, content_id, timestamp, duration
• A content view with duration ≥ 5 minutes must increment the user's MVPA counter within 60 seconds
• A content view with duration < 60 seconds must not count toward MVPA
• User must be able to bookmark the summary for later access from their profile
Validate
• If a summary is archived mid-session while the user is reading it, the page must not break — it must display: "This summary has been temporarily removed for review. Check back soon."
• MVPA counter must increment within 60 seconds of a qualifying 5-minute read event
• A content_view event with duration < 60 seconds must not appear in the user's MVPA tally
• A bookmarked item that becomes paywalled (subscription downgrade) must display the paywall on next visit — the bookmark must be retained
US-2.3 — Search Library Content
User Story As a dental professional, I need to search the study library by keyword so that I can quickly find summaries on specific topics without browsing every category.
Acceptance Criteria
• Search must query against title_arabic, title_english, and subject_tags
• Minimum query length: 2 characters
• Results must return within 500ms for a library of up to 10,000 items
• Results must display: title, subject tags, difficulty, last_reviewed_date, access status
• Zero results must display: "No results found for '[query]'. Try searching for a related topic or browse by subject." with subject browse links — never a blank page
• Search must be diacritics-insensitive — searching اسنان must return results containing أسنان
Validate
• Search must only return items with status = published — archived or draft items must never appear
• Paywalled items must appear in results with a lock icon — not be hidden
• An empty query with filters applied must be valid and return all items matching the filters
• Searching in English on the Arabic interface must return results from the title_english field without error
• Pasting a string longer than 500 characters into the search box must truncate to 100 characters and proceed — no error displayed
US-2.4 — Filter Library Content
User Story As a dental professional preparing for the DHA exam, I need to filter the study library by exam type and subject so that I can focus only on content relevant to my preparation.
Acceptance Criteria
• Filter panel must offer: subject (multi-select), difficulty_level (multi-select), exam_relevance (multi-select), language (single-select), reviewed_within (single-select: last 30 days / 3 months / 6 months)
• Applied filters and search query must be preserved in the URL — a shared URL must produce the same results for another user with the same subscription tier
• Applying filters that produce zero results must display: "No results match your filters. Try removing some filters." with a one-click Clear all filters option
Validate
• Applying filters that produce zero accessible results for the user's tier must display: "No results match your filters in your current plan. [X] results are available in Professional Plus." with upgrade CTA
• Clearing all filters must return the user to the full unfiltered library in their tier
• Filter state must persist across a page refresh
US-2.5 — Auto-Archive Stale Content
User Story As a platform admin, I need the system to automatically archive content that has not been reviewed within 6 months so that the brand promise of fresh, verified content is always enforced without manual intervention.
Acceptance Criteria
• A scheduled job must run daily at 02:00 UTC
• The job must query all content where review_due_date < today and status = published
• For each matching item: status must be set to archived; a content_audit_log entry must be created with action = auto_archived, actor_id = null, timestamp
• Revenue share for archived content must be paused: revenue_share_active = false on the associated revenue share record
• Editorial team must receive a notification listing all items archived in the run
• At Day 150 (30 days before expiry): editorial dashboard must highlight items approaching review due date
Validate
• The job must be idempotent — running it twice on the same day must not double-archive or double-notify
• An already-archived item must not be re-archived by the job — the job must check status before taking action
• An archived item must disappear from all user-facing library views within 24 hours of archiving
• The content_audit_log entry for the auto-archive action must have actor_id = null — confirming it was a system action, not a human action
• Revenue share must resume when the archived item is restored to published
US-2.6 — Mark Content as Reviewed
User Story As a platform admin, I need to mark a content item as reviewed so that its review date is reset, it remains published, and the auto-archive clock restarts.
Acceptance Criteria
• CMS review queue must display all items with review_flag = true (within 15 days of expiry) or status = archived
• "Mark as Reviewed" button must be available on each item in the review queue
• On clicking Mark as Reviewed: last_reviewed_date = today, review_due_date = today + 180 days, review_flag = false, status = published
• A content_audit_log entry must be created: action = reviewed, actor_id = [admin user_id]
• A restored archived item must reappear in user-facing library views within 5 minutes
Validate
• An item restored from archived must reappear in search results within 5 minutes
• The updated last_reviewed_date must immediately display on the item's library card as the new review date
• Revenue share must resume from the date of restoration — no retroactive revenue share for the archived period
• A content_audit_log record must exist for every Mark as Reviewed action with the correct actor_id
US-2.7 — Create Content in the CMS
User Story As a content creator, I need to create and submit a new study summary in the CMS so that it can be reviewed by the editorial team and published to the library.
Acceptance Criteria
• CMS editor must support Arabic RTL Markdown with live preview rendering content exactly as it will appear to users
• Required fields before submission: title_arabic, title_english, body_arabic (minimum 200 characters), subject_tags, vertical, difficulty_level
• On submission: content status set to submitted_for_review; content is locked for editing; platform admin receives a notification
• content_creator can only edit content in draft or rejected status — submitted content is locked
Validate
• Attempting to submit with body_arabic under 200 characters must show inline validation — the submit button must be disabled
• A content creator attempting to edit a submitted item must see: "Your content is under review and cannot be edited. You will be notified when the review is complete."
• A submitted item must appear in the platform admin review queue within 5 minutes
• All CMS actions must create a content_audit_log entry with the actor's user ID and timestamp
US-2.8 — Review and Publish Content
User Story As a platform admin, I need to approve and publish submitted content so that verified, quality-checked summaries become available to subscribers.
Acceptance Criteria
• Review queue must be sorted by submission date ascending (oldest first) and filterable by content type and vertical
• Approve action: sets status = approved then status = published; last_reviewed_date set to today; review_due_date set to today + 180 days; content creator notified
• Reject action: requires mandatory rejection_reason (minimum 20 characters); sets status = rejected; content creator receives rejection reason and can resubmit
• A published item must appear in the user-facing library within 5 minutes
• A content_creator cannot publish their own content — the publish action is restricted to platform_admin
Validate
• Attempting to reject without a rejection_reason must block the action — the reject button must be disabled until the reason field has ≥ 20 characters
• A newly published item must have review_due_date = today + 180 days — the auto-archive clock starts from publish date
• Two platform admins reviewing the same item simultaneously must trigger optimistic locking — the second admin's submission must display: "This content was just updated by another reviewer. Please refresh and review the current version."
• A rejected content creator must receive the rejection reason and a link to resubmit
US-2.9 — View Revenue Share Dashboard
User Story As a content creator, I need to view my revenue share earnings, cap status, and payout history so that I can track my income from content I have produced.
Acceptance Criteria
• Dashboard must display: total lifetime earnings, this month's earnings, cap status per content item ([Earned EGP X] of [Cap EGP Y]), current rate (30% or 3%), pending payout, next payout date, payout history
• When revenue_share_earned reaches revenue_share_cap on an item: share_rate transitions to 3% automatically; content creator receives email: "Your [content title] has reached its production cap. Your rate has transitioned to 3% residual."
• Revenue share is paused for archived content — dashboard must show paused status for affected items
Validate
• Cap calculation must be: cap_amount = estimated_production_hours × EGP 500 × 5 — set at partnership creation and immutable thereafter
• The rate transition from 30% to 3% must occur at the transaction level — not batch-corrected; if two simultaneous transactions push an item over the cap, database-level locking must ensure the second transaction correctly applies the post-cap rate
• Revenue share transactions for a refunded subscription must be reversed — cap_remaining must be restored accordingly
• A paused revenue share item must show paused status on the dashboard — not 0% earned
Epic 3: Exam Preparation
This epic covers the Egyptian Licensing Exam Question Bank and the Basic Quiz Engine.
The objective is to deliver the must-win commercial product — the only Arabic-language question bank for the Egyptian Health Council licensing exam, with a fully functional timed quiz engine.
US-3.1 — Browse the Exam Question Bank
User Story As a dental student preparing for the Egyptian licensing exam, I need to browse available question bank topics so that I can understand what is covered and choose where to focus my preparation.
Acceptance Criteria
• Exam prep home must display the question bank organised by subject, showing question count per subject
• Each subject must show: available question count, user's completion rate (questions attempted / total available), user's accuracy rate per subject
• Access rules: freemium = 10 sample questions; Starter = 200 questions; Professional Plus = all 800+ questions
Validate
• A freemium user must not be able to access more than 10 questions per session regardless of client-side manipulation — server-side access control must enforce this
• A subject with no available questions (all flagged) must display: "Questions in [subject] are currently under review. Please try a different subject."
• A user who has answered all available questions in their tier must see: "You have answered all available questions in your plan. Upgrade to Professional Plus to access [X] more."
US-3.2 — Start a Practice Quiz
User Story As a dental student, I need to configure and start a practice quiz by selecting subject, question count, and difficulty so that I can practise targeted exam questions at my own pace.
Acceptance Criteria
• Quiz configuration screen must allow selection of: exam_type, subject_filter (or "all subjects"), question_count (10 / 20 / 30 / 50), difficulty_filter (easy / medium / hard / mixed), timed_mode (default on)
• Timer: 90 seconds per question; total session timer displayed; timer pauses when user pauses session
• Questions must be assembled randomly from the eligible bank — no question may repeat within a session
• Quiz session state (current question, answers, time elapsed) must be stored in Redis with 3-hour TTL — session resumes if browser is closed and reopened within 3 hours
Validate
• If the question bank has fewer questions than the requested count for the selected filters: display "Only [X] questions are available for your selected filters. Would you like to start a [X]-question quiz instead?"
• Losing internet connection mid-quiz and reconnecting within the session must resume exactly where the user left off — timer continues from where it stopped (server-side timer state)
• A user attempting to start a second quiz while one is in progress must see: "You have an unfinished quiz. Would you like to continue it or start a new one? Starting a new one will mark the current quiz as abandoned."
• A quiz session in_progress for more than 4 hours must be automatically set to abandoned — answers up to that point must be saved but the session must not be scored
US-3.3 — Answer a Quiz Question
User Story As a dental student in an active quiz session, I need to select an answer and immediately see whether it is correct, along with a full Arabic explanation, so that I can learn from each question as I go.
Acceptance Criteria
• One question displayed at a time with 4 or 5 answer options in Arabic
• Answer is locked on selection — cannot be changed after submission
• On answer selection: correct/incorrect status revealed immediately with visual feedback (green = correct, red = incorrect)
• Full Arabic explanation displayed below — explaining why the correct answer is correct and why each incorrect answer is wrong
• Progress indicator must show: "Question [X] of [Y]"
• Flag question option must be available from the explanation screen
Validate
• An answer cannot be changed after it has been selected — attempting to change via client-side manipulation must return the locked answer
• The explanation must display for every question — a question with an empty explanation_arabic must never be published (enforced at CMS level)
• Flagging a question from the explanation screen must create a question_flag record linked to the correct question_id and the authenticated user's user_id
• A user who has already flagged a question must see: "You have already flagged this question." if they attempt to flag it again
US-3.4 — Complete a Quiz and View Results
User Story As a dental student, I need to view my quiz results with a subject-by-subject breakdown so that I can identify my weak areas and prioritise my remaining study time.
Acceptance Criteria
• Results screen must display: overall score ([X] of [Y] correct, [Z]%), time taken, subject breakdown (% correct per subject), full question list with user's answer, correct answer, and explanation
• If score ≥ 70%: display option to earn a session completion certificate
• Results are permanently stored — they cannot be deleted by the user and feed the Phase 2 analytics and adaptive engine
Validate
• Subject breakdown must correctly reflect percentage of correct answers per subject — not overall score applied uniformly to all subjects
• A quiz where the timer expired must show: unanswered questions marked as incorrect; time taken = full session time limit
• A certificate trigger at 70%+ must correctly link to the certificate generation flow (Feature 5.1)
• Results data must be queryable for future analytics — the session record must include user_id, question_ids, user_answers, subject_scores, score_percentage, completed_at
US-3.5 — Flag an Inaccurate Question
User Story As a dental professional, I need to flag a question I believe is inaccurate or outdated so that the editorial team can review and correct it before it misleads other students.
Acceptance Criteria
• Flag option available on every question during a quiz session and on the results screen
• Flag form must collect: flag_reason (inaccurate / outdated / unclear / duplicate), flag_detail (optional text)
• Each user can flag a given question only once
• When a question reaches 3 open flags: status automatically set to flagged; question hidden from all users; editorial team notification sent within 1 hour
Validate
• A second flag attempt on the same question by the same user must display: "You have already flagged this question."
• A question reaching its 3rd flag must be hidden from all users within 1 hour — the hourly auto-flag job must enforce this
• A flagged question that is dismissed as invalid must have flag_count decremented and status returned to published
• A question that is flagged mid-session must not be removed from the current session — it takes effect for all future sessions
Epic 4: Tutoring Marketplace
This epic covers Tutor Profile Listing, Session Booking, Session Room, Payment Escrow, Rating and Review, No-Show and Cancellation Enforcement, and Tutor Wallet and Payout.
The objective is to deliver a fully operational two-sided tutoring marketplace — students can find, book, and pay for sessions; tutors can list, host, and get paid; and every transaction is protected by escrow and governed by automated policy enforcement.
US-4.1 — Browse Tutor Listings
User Story As a dental student, I need to browse a directory of verified tutors filtered by specialty and exam type so that I can identify the right tutor for my specific preparation needs.
Acceptance Criteria
• Tutor listing must display each tutor card with: profile photo, name_arabic (primary), name_english (secondary), verification badges, specialty tags, session types, price per session, average rating, completed sessions count, next available slot, languages
• Only tutors with tutor_account.status = active must appear — suspended or inactive tutors must never display
• A tutor with zero completed sessions must appear at the bottom of default sort with a "New tutor" label
• Search and filter options: specialty, exam type, session type, price range, rating, language, availability date, verification level
• Default sort: relevance score (composite of rating × session count × response rate)
• Listing must load within 1 second for up to 500 active tutors
Validate
• A tutor without graduate_verified status must not appear in any search result regardless of other filters
• Applying filters that produce no results must display: "No tutors match your filters. Try broadening your search." with a one-click Clear all filters option
• A tutor whose account is suspended between a student's search and booking attempt must show a disabled booking button on refresh
• Searching for a specialty with no verified tutors must display: "No tutors are currently available for [Specialty]. We are recruiting tutors in this area. Leave your email to be notified when one joins." with email capture
US-4.2 — View a Tutor's Full Profile
User Story As a dental student, I need to view a tutor's full profile including their qualifications, session history, and recent reviews so that I can make an informed decision before booking.
Acceptance Criteria
• Full profile must display all card fields plus: bio_arabic + bio_english, education history, session types offered, last 10 reviews with rating, feedback text, and subject tags, full 4-week availability calendar, total sessions completed
• Tutor earnings must never be displayed publicly — not on the profile page nor in any user-facing context
• Book a session CTA must be prominent and accessible without scrolling on desktop
Validate
• Tutor lifetime earnings, wallet balance, and payout history must return 403 for any non-tutor, non-admin API request

US-5.1 — Earn and Download a Certificate

Acceptance Criteria
• Every save action in the CMS must create a new content_version record with: version_id, content_id, version_number (auto-incremented per content item), body_arabic, body_english, edited_by, edited_at, change_summary
• Platform admin must be able to view version history for any content item and restore any previous version
• Content versions must be retained for 12 months then purged by a scheduled cleanup job
• The cleanup job must be idempotent
Validate
• Restoring a previous version must create a new version record reflecting the restoration — not overwrite the current version silently
• The version history must show the editor's name and timestamp for every version
• The 12-month purge job must not delete versions of content items that are currently in published status — only historical versions of archived or retired content
US-8.3 — Secure the Admin and CMS Routes
User Story As a security-conscious platform, I need all admin and CMS routes to return 403 for unauthorised requests so that the existence and structure of admin tooling is never disclosed to attackers.
Acceptance Criteria
• All /admin/* routes must return 403 (not 404) for unauthenticated or unauthorised requests
• All CMS routes require authentication AND either platform_admin or content_creator role — any other role returns 403
• platform_admin accounts must require 2FA to access the admin panel
• Admin panel access from unrecognised IP addresses must trigger a 2FA challenge
Validate
• An unauthenticated request to /admin/cms must return 403 — not a redirect to login and not 404
• A student role user attempting to access any /admin/* route via API must receive 403
• A platform_admin attempting to log into the admin panel from a new IP must be prompted for 2FA before access is granted
• All admin actions (login, content management, user management) must be logged with: timestamp, admin user_id, action, IP address
